## 产出

### 1. 第三期设计评审 `docs/review/2026-10-01-design-review-3.md`

首次针对「照片很多」的专项体检，产出 **R20–R41**：

| # | 发现 | 级别 |
|---|---|---|
| R20 | `stop()` 重建 `scope`，但 ConnectionManager/ThumbnailProvider/TransferEngine 按值捕获旧 scope → **旋转后 USB 连接静默失效** | 🔴 |
| R21 | **RAW+JPEG 选「全部」只传 RAW，JPEG 静默丢弃**（`buildTransferList` 每 group 只产出一个 handle） | 🔴 丢片 |
| R22 | 传输预览 `totalGroups` 在 `.take(6)` 之后取值 → 组数封顶 6、「+N more」恒 0 | 🔴 |
| R23 | `groupByBaseFilename` 仅按文件名聚合 → **双卡/多文件夹同名照片被合并丢一张**，且 `items(key=baseName)` 有重复 key 崩溃隐患 | 🔴 丢片 |
| R24 | 勾选读 `selectedCount` → 整块 `BrowsingContent` 重组，重算 `filterIsInstance`×3 + `count`×2 + `getNewPhotoCount()`（每张一次 SharedPreferences 读） | 🟠 |
| R25 | BY_DATE 每个 section 全量 filter 且**每张新建 `SimpleDateFormat`**（O(分区×照片)） | 🟠 |
| R26 | 选择集 `SnapshotStateList<Int>` 线性：`selectAll` O(n²)、判定 O(k)、预览 O(n·k) | 🟠 |
| R27 | `listPhotos` 前先 `countObjectsInStorage` 完整 BFS 一遍（**MTP 树枚举两遍**） | 🟠 |
| R28 | 缩略图预载仅 50、缓存小、请求不可取消、`rotateByDegrees` 未 recycle 源图 | 🟠 |
| R29 | 枚举满 30 张切 Browsing 后**界面静默**，计数长期是半成品 | 🟠 |
| R30 | `PhotoSyncManager` 去重表**无上限增长** | 🟠 |
| R31–R35 | 刷新指示恒 false / `runCatching` 吞取消 + temp 泄漏 / 详情页下整份 NEF / 死代码与连接泄漏 / BLE 残留资源与 `ObsoleteSdkInt` | 🟡 |
| R36–R41 | lint 明细：`Recycle` 为**误报**（均用 `?.use{}`）、证书 Typos 误报、未用资源、AutoboxingState、UseKtx | 🟡 |

> 评分：工程 **B** / 产品 **B**（较第二期 B+/B+ 下调半档）——两期都在做正确性止血，**「大库可用性」直到用户实操才暴露，且含两项丢片级缺陷**；根因是测试数据长期只有个位数照片，未把「照片多」当常态验证。
